# Planeweave — роадмап разработки (курсовой проект)

**Дата:** 2026-07-28  
**Статус:** утверждён  
**Аудитория:** junior-разработчики (6–12 месяцев опыта), команды 2–3 человека  
**Длительность:** 10 недель  
**Стек:** TypeScript, React, ReactFlow (фронтенд); Go (бекенд — готовит ментор)

---

## 1. Описание продукта

**Planeweave** — командная доска задач, где задачи отображаются как узлы графа, а зависимости — как направленные связи между ними. Несколько участников редактируют одну доску одновременно; изменения видны в реальном времени.

### Ключевые возможности

- Регистрация и вход (email + пароль)
- Создание проекта и приглашение участников по ссылке или email
- Доска с задачами на канвасе (граф)
- Зависимости между задачами («задача B заблокирована задачей A»)
- Строгий DAG — циклические зависимости запрещены
- Синхронизация изменений между участниками через WebSocket

### Сущности

| Сущность | Поля |
|----------|------|
| **Пользователь** | email, пароль, отображаемое имя |
| **Проект** | название, владелец, список участников |
| **Задача** | название, статус (`todo` / `in_progress` / `done`), исполнитель (id пользователя), позиция на канвасе (x, y) |
| **Зависимость** | направленная связь: from → to (from блокирует to) |

### Ограничения

- Граф зависимостей — **строгий DAG** (без циклов)
- Окончательная проверка ацикличности — на бекенде (код 409)
- На фронтенде — предварительная проверка с мгновенным сообщением пользователю

## 3. Подход к разработке

Выбран **горизонтальный подход**: каждая неделя — один слой системы, вся команда работает над одной темой. Это снижает риск конфликтов при слиянии и упрощает менторство для junior-аудитории.

**Библиотека графов:** ReactFlow (`@xyflow/react`) — нативная интеграция с React, встроенное перетаскивание, хорошая документация.

## 4. Роадмап по неделям

### Неделя 1 — Техническое задание

**Цель:** студенты самостоятельно пишут ТЗ на основе product brief ментора.

**Формат:** шаблон [`docs/course/tz-template.md`](../../course/tz-template.md) — структура близка к учебному примеру [`docs/examples/ВКР ТЗ.pdf`](../../examples/ВКР%20ТЗ.pdf) (введение → назначение → требования → приёмка → стадии), но **без** объёма ВКР: без ТЭО, правовых оснований, Docker-маркировки и нагрузочных испытаний.

**Результаты команды:**
- **§1 Введение:** наименование, область применения, актуальность, стек (кратко)
- **§2 Назначение и цели:** назначение системы, 3–5 целей, роли пользователей
- **§3 Функциональное назначение:** обзор фронтенда и использования API ментора
- **§4 Требования:** пользовательские истории (8–10) с критериями приёмки; экраны и переходы; модель данных; таблица REST-точек и WebSocket-событий; нефункциональные требования
- **§5–6:** критерии приёмки ТЗ и таблица стадий по 10 неделям курса
- Открытые вопросы (если остались)

**Критерий зачёта:** ТЗ утверждено ментором; нет пробелов в сценариях авторизации, приглашений, CRUD задач и синхронизации.

**Ментор:** выдаёт product brief (1–2 страницы), шаблон ТЗ, ревьюит PR за 2–3 дня.

**Цель:** студенты проектируют интерфейс до начала кодирования.

**Результаты:**
- Каркасы всех экранов (Figma, Excalidraw или аналог)

**Критерий зачёта:** макеты утверждены; понятно расположение графа, форм и списка участников.

### Неделя 3 — Каркас приложения и авторизация

**Цель:** поднять React-проект и подключиться к API ментора.

**Стек фронтенда:**
- Vite + React + TypeScript
- React Router
- TanStack Query (REST-запросы)
- Zustand (состояние сессии и интерфейса)

**Задачи:**

- Защищённые маршруты
- Выход из системы

**Критерий зачёта:** пользователь регистрируется, входит и попадает на пустую панель проектов.

### Неделя 4 — Проекты и приглашения

**Задачи:**
- Список проектов пользователя
- Создание, переименование, удаление проекта
- Настройки проекта: список участников
- Приглашение: генерация ссылки (+ email, если есть в API)
- Принятие приглашения (страница `/invite/:token`)

**Критерий зачёта:** 2–3 участника команды оказываются в одном проекте через приглашение.

### Неделя 5 — Граф: отображение (только чтение)

**Задачи:**
- Интеграция ReactFlow
- Пользовательский узел: название, метка статуса, исполнитель
- Пользовательское ребро: направленная стрелка зависимости
- Загрузка задач и зависимостей через REST
- Перемещение и масштабирование канваса; мини-карта (по желанию)
- Позиции узлов из API (x, y), авто-расстановка не обязательна

**Критерий зачёта:** доска показывает задачи и связи; клик по задаче открывает боковую панель (только чтение).

---

### Неделя 6 — Редактирование доски и проверка DAG

**Задачи:**
- Создание задачи (кнопка и/или клик на канвас)
- Редактирование: название, статус, исполнитель
- Перетаскивание узла → сохранение позиции через API
- Создание зависимости: перетаскивание от точки соединения одной задачи к другой
- Удаление задачи и связи
- Проверка DAG на клиенте: при попытке создать цикл — всплывающее сообщение, связь не создаётся
- Оптимистичные обновления через TanStack Query

**Критерий зачёта:** граф из 5+ задач с зависимостями; цикл заблокирован на интерфейсе.

---

### Неделя 7 — Синхронизация в реальном времени

**Задачи:**
- WebSocket-клиент (переподключение, проверка связи)
- Подписка на комнату проекта
- Обработка событий: `task.created`, `task.updated`, `task.deleted`, `task.moved`, `dependency.created`, `dependency.deleted`
- Слияние удалённых событий с локальным состоянием (без конфликта с оптимистичными обновлениями)
- Индикатор «N человек онлайн» (если есть в API)

**Критерий зачёта:** изменение в одном браузере мгновенно видно в другом.

---

### Неделя 8 — Обработка ошибок и граничные случаи

**Задачи:**
- Заглушки загрузки, пустые состояния
- Граница ошибок React вокруг доски
- Всплывающие сообщения при ошибках API (401 → вход, 403 → нет доступа, 409 → цикл)
- Плашка при разрыве WebSocket: «Переподключение…»
- Валидация форм (обязательное название задачи и т.п.)

**Критерий зачёта:** CI проходит, минимум 8 тестов.

## 6. Потоки данных

### Создание задачи

```
Клик «Добавить задачу»
  → форма (название обязательно)
  → POST /projects/:id/tasks { title, x, y }
  → оптимистично: узел на канвасе
  → ответ сервера: id задачи
  → событие task.created → другие участники добавляют узел
  → при ошибке: откат + сообщение
```

### Создание зависимости

```
Перетаскивание от задачи A к задаче B
  → локально: обход графа (достижима ли A из B?)
  → цикл: связь не рисуется, сообщение «Циклическая зависимость запрещена»
  → иначе: POST /dependencies { from: A, to: B }
  → оптимистично: ребро на канвасе
  → событие dependency.created → синхронизация
  → 409 от сервера: откат + сообщение
```

### Синхронизация

```
Участник 1 меняет статус
  → PATCH /tasks/:id { status }
  → сервер рассылает task.updated
  → участник 2: обновление кэша Query → перерисовка узла
```

**Разрыв WebSocket:** плашка «Соединение потеряно»; переподключение с задержкой 1с → 2с → 4с → … (макс. 30с); после восстановления — полная загрузка через REST.

**Конфликт с оптимистичным обновлением:** событие от инициатора игнорируется, если локальное состояние уже актуально (по id + версии или времени изменения).

## 7. Обработка ошибок

| Код / ситуация | Поведение |
|----------------|-----------|
| 401 | перенаправление на вход |
| 403 | экран «Нет доступа» |
| 404 | сообщение + возврат к списку проектов |
| 409 | откат связи + «Циклическая зависимость» |
| 422 | подсветка полей формы |
| 500 / сеть | «Не удалось выполнить действие» |
| WebSocket недоступен | плашка переподключения; REST работает |

**Пустые состояния:** нет проектов → «Создайте первый проект»; нет задач → «Добавьте первую задачу».
